# Homelab k3s Guide

On-prem distributed stack on 3 Raspberry Pis: k3s, PostgreSQL, Redis, web app, queue workers, batch jobs.

## 1. Resource audit (2026-11-07)

| | pi4-8gb (`hien-pi-4b`) | pi4-4gb (`hien-pi-4b-4gb`) | pi3 (`hien-pi-3b`) |
|---|---|---|---|
| IP (static) | 192.168.40.250 | 192.168.40.251 | 192.168.40.252 |
| Board | Pi 4B rev 1.5 | Pi 4B rev 1.1 | Pi 3B+ |
| CPU | 4 cores A72 | 4 cores A72 | 4 cores A53 |
| RAM | 7.6 GiB | 3.7 GiB | 905 MiB |
| Disk | 32 GB SD | 64 GB SD | 32 GB SD |
| OS | Debian 13 trixie, arm64, kernel 6.12 | same | same |
| Power (`get_throttled`) | `0x0` OK | `0x50000` under-voltage happened before | `0x50005` **under-voltage now** |
| Running now | nginx :80, php8.4-fpm | nothing | nginx :80, **cloudflared** |

### Blockers to fix before installing

1. **Memory cgroup disabled** on all nodes (`cgroup_disable=memory` in cmdline, `memory` missing from `/sys/fs/cgroup/cgroup.controllers`). k3s will not start without it.
2. **pi3 is under-voltage right now**, and pi4-4gb was under-voltage earlier. Use the official PSUs (Pi 4: 5V/3A USB-C, Pi 3B+: 5V/2.5A micro-USB) and short, thick cables. Under-voltage corrupts SD cards and the k3s datastore.
3. ~~IPs come from DHCP.~~ **Done 2026-11-07:** static IPs .250/.251/.252 set via NetworkManager (HUMAX router has no reservation, pool .2–.254 is fixed).
4. **Port 80 is taken** by host nginx on pi3 and pi4-8gb. k3s ServiceLB/Traefik needs 80/443 on the nodes.
5. **Everything is on SD cards.** That is fine for k3s itself (with the SQLite datastore), but it is bad for PostgreSQL (wear, slow fsync). **Strongly recommended: a USB 3 SSD on pi4-8gb** (any 120 GB+ SATA SSD plus a UASP adapter, or a USB NVMe enclosure).
6. ~~Stale Cloudflare tunnel target~~ **Done:** `pi4.hien.qzz.io` → `192.168.40.250`.

## 2. Architecture

System design diagrams (request/data flow, node placement) live in
[README.md → System design](README.md#system-design). They are generated by
`scripts/diagrams.py` and kept current; this guide does not duplicate them.

### Node roles (target)

| Node | k3s role | Runs | Budget |
|---|---|---|---|
| **pi4-8gb** | server (control plane, SQLite datastore) | k3s server, PostgreSQL, Redis, Traefik | ~1 GB k3s, 2 GB PG, 512 MB Redis, rest headroom |
| **pi4-4gb** | agent | web app, queue workers, batch Jobs | ~3 GB for apps |
| **pi3** | agent, tainted `light` | cloudflared, small exporters/cron | ~500 MB usable. Nothing heavy. |

Design decisions:
- **Single server, no HA.** HA needs 3 servers running etcd, and etcd on SD cards plus 1 GB on pi3 is a bad fit. Mitigate with datastore + DB backups. You can rebuild the control plane in about 15 minutes.
- **Data is pinned to pi4-8gb** (local-path volumes on the SSD). Stateless apps can float.
- **Redis is both cache and queue.** It is simple and fast enough for a homelab. Use Redis Streams, BullMQ (Node), Celery/RQ/Arq (Python), or Asynq (Go).
- **Batch** = k8s `CronJob` for schedules and `Job` for one-offs. **KEDA** scales workers on queue length.
- **Exposure** via Cloudflare Tunnel running inside the cluster. No open router ports, free TLS.
- **Images** are built on the Mac (Apple Silicon = arm64 native) and pushed to GHCR.

## 3. Prepare nodes (all 3)

### 3.1 Fix power + DHCP reservations
Do this physically / in the router first. Check afterwards: `vcgencmd get_throttled` should print `0x0` after a reboot under load.

### 3.2 Enable memory cgroup, update, reboot
```bash
for h in pi3 pi4-8gb pi4-4gb; do
  ssh $h 'sudo sed -i "1 s/\$/ cgroup_enable=memory/" /boot/firmware/cmdline.txt &&
          sudo apt-get update && sudo apt-get -y full-upgrade &&
          sudo apt-get -y install curl nfs-common open-iscsi jq &&
          sudo reboot'
done
# after reboot, should list "memory":
for h in pi3 pi4-8gb pi4-4gb; do ssh $h 'echo $(hostname): $(cat /sys/fs/cgroup/cgroup.controllers)'; done
```

### 3.3 Free port 80
Back up anything you need from host nginx first (`/var/www`, `/etc/nginx/sites-available`), then:
```bash
ssh pi4-8gb 'sudo systemctl disable --now nginx php8.4-fpm'
ssh pi3     'sudo systemctl disable --now nginx'
```
The site served at `hien.qzz.io` goes down until it is migrated into k3s (step 8). Keep host `cloudflared` running until then.

### 3.4 (Recommended) Mount SSD on pi4-8gb
```bash
ssh pi4-8gb
lsblk                       # find the SSD, e.g. /dev/sda
sudo mkfs.ext4 -L ssd /dev/sda      # DESTROYS data on /dev/sda
sudo mkdir -p /mnt/ssd
echo 'LABEL=ssd /mnt/ssd ext4 defaults,noatime 0 2' | sudo tee -a /etc/fstab
sudo mount -a && sudo mkdir -p /mnt/ssd/k3s-storage
```

## 5. PostgreSQL (CloudNativePG)

CNPG gives you failover-ready Postgres, scheduled backups, and a `-rw` service. It supports arm64.

```bash
helm repo add cnpg https://cloudnative-pg.github.io/charts
helm upgrade --install cnpg cnpg/cloudnative-pg -n cnpg-system --create-namespace
```

`k8s/data/postgres.yaml`:
```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata: { name: pg, namespace: data }
spec:
  instances: 1                      # single node with data; raise when you add SSD to pi4-4gb
  imageName: ghcr.io/cloudnative-pg/postgresql:17
  storage: { size: 40Gi, storageClass: local-path }
  affinity:
    nodeSelector: { role: data }
  resources:
    requests: { cpu: 500m, memory: 1Gi }
    limits:   { memory: 2Gi }
  postgresql:
    parameters:
      shared_buffers: 512MB
      effective_cache_size: 1536MB
      max_connections: "100"
      wal_compression: "on"
  bootstrap:
    initdb: { database: app, owner: app }   # creates secret pg-app (user/password/uri)
```
```bash
kubectl apply -f k8s/data/postgres.yaml
kubectl -n data get cluster pg
kubectl -n data get secret pg-app -o jsonpath='{.data.uri}' | base64 -d   # connection string
```
In-cluster DSN host: `pg-rw.data.svc:5432`.

## 6. Redis (cache + queue)

Use a plain manifest with the official image. Avoid Bitnami charts (their free images were discontinued in 2025).

`k8s/data/redis.yaml`:
```yaml
apiVersion: v1
kind: Service
metadata: { name: redis, namespace: data }
spec:
  selector: { app: redis }
  ports: [{ port: 6379 }]
---
apiVersion: apps/v1
kind: StatefulSet
metadata: { name: redis, namespace: data }
spec:
  serviceName: redis
  replicas: 1
  selector: { matchLabels: { app: redis } }
  template:
    metadata: { labels: { app: redis } }
    spec:
      nodeSelector: { role: data }
      containers:
        - name: redis
          image: redis:8-alpine
          args: ["--appendonly", "yes", "--maxmemory", "400mb",
                 "--maxmemory-policy", "noeviction",          # queue: never drop jobs
                 "--requirepass", "$(REDIS_PASSWORD)"]
          env:
            - name: REDIS_PASSWORD
              valueFrom: { secretKeyRef: { name: redis, key: password } }
          ports: [{ containerPort: 6379 }]
          resources:
            requests: { cpu: 100m, memory: 256Mi }
            limits:   { memory: 512Mi }
          volumeMounts: [{ name: data, mountPath: /data }]
  volumeClaimTemplates:
    - metadata: { name: data }
      spec:
        accessModes: [ReadWriteOnce]
        storageClassName: local-path
        resources: { requests: { storage: 5Gi } }
```
```bash
kubectl -n data create secret generic redis --from-literal=password="$(openssl rand -hex 24)"
kubectl apply -f k8s/data/redis.yaml
```
Note: `noeviction` is right for a queue. If you also want an LRU cache, run a second small Redis with `allkeys-lru` instead of mixing the two.

### 7.4 Queue workers + autoscale with KEDA
```bash
helm repo add kedacore https://kedacore.github.io/charts
helm upgrade --install keda kedacore/keda -n keda --create-namespace
```
`k8s/apps/worker.yaml`:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: worker, namespace: apps }
spec:
  replicas: 1
  selector: { matchLabels: { app: worker } }
  template:
    metadata: { labels: { app: worker } }
    spec:
      imagePullSecrets: [{ name: ghcr }]
      terminationGracePeriodSeconds: 60      # let jobs finish on SIGTERM
      containers:
        - name: worker
          image: ghcr.io/<gh-user>/web:0.1.0
          command: ["./worker"]               # same image, different entrypoint
          envFrom: [{ secretRef: { name: app-env } }]
          resources:
            requests: { cpu: 200m, memory: 128Mi }
            limits:   { memory: 512Mi }
---
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: { name: worker, namespace: apps }
spec:
  scaleTargetRef: { name: worker }
  minReplicaCount: 1
  maxReplicaCount: 6
  triggers:
    - type: redis
      metadata:
        address: redis.data.svc:6379
        listName: jobs                 # your queue key (list-based queue)
        listLength: "20"               # 1 replica per 20 pending jobs
      authenticationRef: { name: redis-auth }
---
apiVersion: keda.sh/v1alpha1
kind: TriggerAuthentication
metadata: { name: redis-auth, namespace: apps }
spec:
  secretTargetRef: [{ parameter: password, name: redis-pass, key: password }]
```
```bash
kubectl -n apps create secret generic redis-pass \
  --from-literal=password="$(kubectl -n data get secret redis -o jsonpath='{.data.password}' | base64 -d)"
```
If you use Redis Streams instead of lists, use the `redis-streams` trigger (`stream`, `consumerGroup`, `pendingEntriesCount`).

### 7.5 Batch: CronJob
`k8s/apps/nightly.yaml`:
```yaml
apiVersion: batch/v1
kind: CronJob
metadata: { name: nightly-report, namespace: apps }
spec:
  schedule: "0 2 * * *"
  timeZone: Asia/Tokyo
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 2
      activeDeadlineSeconds: 3600
      template:
        spec:
          restartPolicy: Never
          imagePullSecrets: [{ name: ghcr }]
          nodeSelector: { role: apps }
          containers:
            - name: job
              image: ghcr.io/<gh-user>/web:0.1.0
              command: ["./batch", "nightly-report"]
              envFrom: [{ secretRef: { name: app-env } }]
              resources: { requests: { cpu: 500m, memory: 256Mi }, limits: { memory: 1Gi } }
```
For big one-off fan-out, use a `Job` with `completions: N`, `parallelism: 3`, `completionMode: Indexed` (each pod reads `JOB_COMPLETION_INDEX`).

## 8. Expose via Cloudflare Tunnel (in cluster, on pi3)

Reuse the existing tunnel credentials from pi3:
```bash
ssh pi3 'sudo cat /etc/cloudflared/ab958f58-ce09-42de-a826-bd8a8779bdbd.json' > /tmp/tunnel.json
kubectl -n infra create secret generic tunnel-creds --from-file=credentials.json=/tmp/tunnel.json
rm /tmp/tunnel.json
```
`k8s/infra/cloudflared.yaml`:
```yaml
apiVersion: v1
kind: ConfigMap
metadata: { name: cloudflared, namespace: infra }
data:
  config.yaml: |
    tunnel: ab958f58-ce09-42de-a826-bd8a8779bdbd
    credentials-file: /etc/cloudflared/creds/credentials.json
    metrics: 0.0.0.0:2000
    no-autoupdate: true
    ingress:
      - hostname: "*.hien0ethan.com"
        service: http://traefik.kube-system.svc:80
      - hostname: hien0ethan.com
        service: http://traefik.kube-system.svc:80
      - service: http_status:404
---
apiVersion: apps/v1
kind: Deployment
metadata: { name: cloudflared, namespace: infra }
spec:
  replicas: 2
  selector: { matchLabels: { app: cloudflared } }
  template:
    metadata: { labels: { app: cloudflared } }
    spec:
      tolerations: [{ key: role, value: light, effect: NoSchedule }]
      containers:
        - name: cloudflared
          image: cloudflare/cloudflared:2025.10.0
          args: ["tunnel", "--config", "/etc/cloudflared/config/config.yaml", "run"]
          livenessProbe: { httpGet: { path: /ready, port: 2000 } }
          resources: { requests: { cpu: 20m, memory: 32Mi }, limits: { memory: 128Mi } }
          volumeMounts:
            - { name: config, mountPath: /etc/cloudflared/config }
            - { name: creds,  mountPath: /etc/cloudflared/creds }
      volumes:
        - { name: config, configMap: { name: cloudflared } }
        - { name: creds,  secret: { secretName: tunnel-creds } }
```
Then stop the host one: `ssh pi3 'sudo systemctl disable --now cloudflared'`. DNS already has a proxied wildcard `*` CNAME to the tunnel, so a new subdomain only needs an Ingress rule with that host.

## 9. Backups (plan; deferred by decision 2026-11-08)

**Status: deferred.** No backups run. Accepted risk: losing pi4-8gb's SD card loses Postgres,
Redis, metrics and k3s state (manifests survive in git). Revisit before storing real data.

A backup = a copy stored elsewhere **plus a tested restore**. It covers hardware death (SD card),
mistakes (bad migration, accidental delete) and disaster (only an off-site copy survives).

Why urgent: pi4-8gb's SD card (generic 32 GB, 2022) takes ~537 writes/min, ~12 GiB/day
(measured 2026-11-08), and holds the OS, k3s control plane, Postgres, Redis and metrics.

### 9.1 What to back up

Git + Flux already restore all manifests and Helm values. Backups cover what exists only in the cluster:

| Part | Recreatable without backup? | Method (planned) |
|---|---|---|
| Postgres data | **no**, irreplaceable | CNPG native backup to Cloudflare R2: nightly base backup + continuous WAL (point-in-time restore), 14d retention |
| Secrets (7, see 11.3) | mostly by hand; **tunnel creds: no** (new tunnel + DNS) | SOPS + age, encrypted in git |
| k3s `state.db` + server token | mostly, via Flux | nightly copy to R2 |
| Redis | yes, if jobs can be re-queued | AOF already on disk; copy nightly only if jobs matter |
| Mac: `~/.ssh/id_homelab`, kubeconfig | SSH key lost = locked out of Pis | password manager (user) |

Not backed up: manifests (git), container images, OS (reinstall + this guide), provisioned
Grafana dashboards, metrics history (30d, disposable).

### 9.2 Where: 3-2-1 rule

3 copies, 2 devices, 1 off-site. Off-site = **Cloudflare R2** (S3-compatible, 10 GB free tier,
free egress so restores cost nothing). Optional faster local copy on pi4-4gb (same house, also SD).

### 9.3 Steps

- [ ] Postgres → R2 (CNPG `backup.barmanObjectStore` + `ScheduledBackup`)
- [ ] Restore test: bootstrap a temporary second cluster from the backup, compare row counts
- [ ] Secrets → SOPS-encrypted in git (also removes manual secret recreation on rebuild)
- [ ] k3s `state.db` → R2 nightly
- [ ] User: SSH key + kubeconfig into password manager

### 10.2 Grafana access (LAN only)

Grafana uses Ingress host `grafana.lan`. The Cloudflare tunnel only forwards `*.hien0ethan.com`,
so `grafana.lan` is unreachable from the internet by design.

1. Mac: `echo "192.168.40.250 grafana.lan" | sudo tee -a /etc/hosts`
2. Password: `kubectl -n monitoring get secret grafana-admin -o jsonpath='{.data.admin-password}' | base64 -d`

**Troubleshooting: `curl` works but the browser fails.** Seen 2026-11-08: `/etc/hosts` and
`curl http://grafana.lan` were fine (HTTP 200), the browser failed. Causes:
- Browser upgrades to `https://` (Chrome "Always use secure connections", Safari, Firefox HTTPS-Only).
  Traefik answers 443 with its built-in self-signed cert, so the upgrade fails.
- Chrome treats bare `grafana.lan` as a search; type `http://grafana.lan/`.
- Chrome's own DNS cache: `chrome://net-internals/#dns` → Clear host cache.
- DNS-over-HTTPS (Firefox) or iCloud Private Relay bypass `/etc/hosts`.
- **Chrome `ERR_ADDRESS_UNREACHABLE`** (seen and fixed 2026-11-08): Chrome resolved `grafana.lan`
  correctly (`chrome://net-internals/#dns` → `192.168.40.250`) but could not reach any LAN IP, even
  `http://192.168.40.250/`, while `curl` in Terminal worked.
  - Cause: macOS **Local Network** permission (macOS 15+). Chrome auto-updates run Chrome from a
    temporary copy (`/private/var/folders/.../com.google.Chrome.code_sign_clone/...`). The permission is
    tied to the app's path, so the running copy was effectively denied. Toggling the setting in
    System Settings → Privacy & Security → Local Network did **not** help; neither did ⌘Q.
  - **Fix: open `chrome://restart`.** Chrome relaunched from `/Applications`, macOS showed the
    "allow Google Chrome to access the local network" prompt → **Allow** → works.
  - Still failing? Reboot the Mac, or `tccutil reset LocalNetwork com.google.Chrome` to get the prompt back.
  - May come back after future Chrome auto-updates: same fix.

### 10.3 Grafana HTTPS with a private CA (done 2026-11-08)

`https://grafana.lan` with no browser warning on this Mac, using [mkcert](https://github.com/FiloSottile/mkcert).

1. [x] `brew install mkcert` (Mac)
2. [x] `mkcert -install`: adds a local CA to the macOS keychain (needs sudo, user runs it).
   The CA key stays in `~/Library/Application Support/mkcert/rootCA-key.pem`. Never copy or share it:
   whoever holds it can mint certs this Mac trusts for any site. Remove with `mkcert -uninstall`.
3. [x] Issue cert for `grafana.lan` (expires 2029-02-08), load as TLS secret `monitoring/grafana-lan-tls`, delete local key files.
   Commands: header of `k8s/monitoring/grafana-https.yaml`.
4. [x] Helm values: `grafana.ingress.tls` with that secret, `root_url: https://grafana.lan`; http→https via Traefik
   Middleware `monitoring/redirect-https` (301).
5. [x] Verified: `curl https://grafana.lan` → 200 with system trust; `http://` → 301 to https;
   `grafana.hien0ethan.com` still serves whoami (not public).

Found while doing this: the System keychain also trusted an unrelated, older mkcert CA
(`NTQ-SOLUTION\sy.le@d-os3-sylt`, SHA-256 `DA130CC5…`). Remove it with
`sudo security delete-certificate -Z <sha256> /Library/Keychains/System.keychain`.

Other devices (phone, other laptops) don't trust this CA. For access from anywhere, use
`grafana.hien0ethan.com` behind Cloudflare Access instead.

## 11. GitOps with Flux (2026-11-08)

Flux v2.10.0 runs in `flux-system` and pulls this repo every minute. Day-to-day: edit, commit, push.

### 11.1 Layout

```
clusters/homelab/
  kustomization.yaml          entry point Flux reads
  flux-system/                Flux itself (gotk-components.yaml generated, gotk-sync.yaml)
  platform.yaml               one Flux Kustomization per k8s/ folder + dependsOn order
k8s/
  namespaces/                 prune: false
  releases/                   HelmRepository + HelmRelease (cnpg, vm stack) + vm-stack-values.yaml
  infra/                      cloudflared
  data/                       Postgres (CNPG Cluster), Redis   prune: false
  apps/                       whoami (later: web, workers, cron)
  monitoring/                 VMPodScrapes, Traefik https redirect
```

Order: `namespaces → releases → data → apps`, `namespaces → infra`, `releases → monitoring`.
Each `k8s/<folder>/kustomization.yaml` lists its files; a new manifest must be added there.

### 11.2 How it was installed (no `flux bootstrap`)

`flux bootstrap` needs a GitHub key with **write** access. Instead:
1. `flux install --export > clusters/homelab/flux-system/gotk-components.yaml`, applied with kubectl.
