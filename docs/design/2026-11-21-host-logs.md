# Host logs in Grafana (roadmap O1)

Status: built 2026-11-21

## Problem

Only **pod** logs reach VictoriaLogs. Everything that runs directly on the machines logs to each
machine's systemd **journal** and nowhere else: the backup jobs, Garage, the scheduled checks, the
host apply, k3s itself, SSH logins, and the **kernel** (under-voltage, USB disconnects, disk errors).

Real cost, the same week: the off-site copy failing, Garage's LMDB crash, the SSD's USB resets, the
apply failing: each needed SSH into the right machine, `journalctl`, and copying the output by hand.
And when a machine dies (a frozen Pi, a dead SD card), its last log lines die with it.

## Goals / non-goals

Goals:
- every machine's journal (services + kernel) searchable in Grafana, next to the pod logs
- a machine's logs survive the machine (shipped within seconds)
- no log lost during a short outage of VictoriaLogs or the network
- set up by host GitOps, checked by `verify.yml`

Non-goals: long-term log archive (stays 14 days / 8 GiB), logs leaving the LAN, alerting on log
contents (later, if ever: alerts stay on metrics and SLOs).

## Options considered

| Option | For | Against |
|---|---|---|
| **A. `systemd-journal-upload` on each host → VictoriaLogs' journald endpoint** | part of systemd (no new software to trust); keeps its position in the journal, so after an outage it resumes where it stopped (the journal itself is the buffer); VictoriaLogs speaks this format natively | needs a fixed address for VictoriaLogs reachable from the hosts |
| B. extend the vlagent DaemonSet to read `/var/log/journal` | no new host service | vlagent collects container log files; reading the binary journal needs another agent (Vector, Fluent Bit): new software on every node |
| C. Promtail / Vector / Fluent Bit on the hosts | flexible | one more agent to install, update and secure, for something systemd already does |
| D. syslog forwarding (rsyslog) | very old, common | loses the journal's structured fields (unit, priority, boot id), text parsing again |

## Decision

**A.** The tool comes with systemd, the format keeps every field (`_SYSTEMD_UNIT`, `_HOSTNAME`,
`PRIORITY` → `level`), and resuming from its saved position gives "no loss in an outage" for free.

## Design

```text
 node-workstation, node-8gb, node-4gb, node-1gb                     cluster
 journald ──► systemd-journal-upload ──HTTP──► 10.43.0.50:9428 ──► Service logs-ingest ──► VictoriaLogs (vlsingle)
 (services + kernel)   remembers its position        (fixed ClusterIP, reachable from every node,
                       (/var/lib/systemd/journal-upload)  not from the LAN)
```

| Piece | Where |
|---|---|
| fixed address | site-settings `LOGS_INGEST_IP` (10.43.0.50, in the low "static" part of k3s' service range 10.43.0.0/16; checked in CI) |
| Service `logs-ingest` with that ClusterIP → vlsingle pods | `k8s/monitoring/logs-ingest.yaml` |
| uploader config, restart policy, journald limits | `ansible/playbooks/host-logs.yml` (in `site.yml`: host GitOps) |
| fields | `_HOSTNAME`, `_SYSTEMD_UNIT`, `_MACHINE_ID` are the stream; `level` from `PRIORITY` |

Why a **ClusterIP** and not a NodePort or Ingress: a ClusterIP is reachable from the cluster's own
nodes (kube-proxy on each host) but **not** from other machines on the LAN. VictoriaLogs has no login:
a NodePort would let anyone on the Wi-Fi read every log. Why a **fixed** one: the hosts are
configured by Ansible, not by Kubernetes, so the address must not change on a rebuild.

## Risks and how they are handled

| Risk | Answer |
|---|---|
| everyone on the cluster's nodes can read logs at that address | same as today for pod logs (VictoriaLogs has no auth); not exposed to the LAN. Authentication in front of VictoriaLogs: later, with O5 (security baseline) |
| secrets in host logs | none expected (no_log in Ansible, secrets via files); the journal already holds whatever services print |
| SD-card wear on the Pis | journald capped (`SystemMaxUse=200M`); upload is reading, not writing |
| first upload sends the whole existing journal | one-time; VictoriaLogs drops entries older than its 14-day retention |
| VictoriaLogs down or a rebuild | the uploader keeps its position and retries (`Restart=always`); nothing is lost while the journal still holds it |
| the fixed IP clashes with another Service | 10.43.0.50 is in the low part of the range that Kubernetes leaves to fixed IPs (automatic IPs come from the top); CI checks the setting |
| log volume | host logs are a few MB per day per machine; counted in the same 14 days / 8 GiB |

## Test plan

Before merging (done 2026-11-21, locally):
- VictoriaLogs v1.53.0 (the version we run): `POST /insert/journald/upload` accepted (200), plain
  `/insert/journald` refused (400): the uploader adds `/upload` itself.
- the real `systemd-journal-upload` (Debian) with `--url=http://…/insert/journald` sent a journal
  entry; in VictoriaLogs it had `_HOSTNAME`, `_SYSTEMD_UNIT`, `_msg`, and `PRIORITY=4` became `level`.
- playbooks pass CI (syntax + task loading with the workstation's Ansible version).

After deploying:
- the apply's smoke test: each host reaches `http://10.43.0.50:9428/health`
- `verify.yml`: every machine in the inventory sent log lines in the last 15 minutes
- in Grafana: `_SYSTEMD_UNIT:=homelab-offsite.service` shows the off-site job, `undervoltage` the kernel

## Rollback

Revert the PR (removes the Service and the playbook from host GitOps). Removing a playbook does not
undo what it already did, so then once: `sudo systemctl disable --now systemd-journal-upload` on each
host (or an apply with a task that does it). Nothing else depends on the uploader; each machine's
journal keeps working as before.
